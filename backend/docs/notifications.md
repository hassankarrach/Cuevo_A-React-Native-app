# In-app notification API

The authenticated `/api/v1/notifications` API stores durable in-app
notifications for one recipient account. It is not a native notification or
push service: OS permission prompts, device-token registration and push-provider
delivery are not implemented. The mobile app can translate `kind` identifiers
to localized presentation; it must not parse a server message string.

All endpoints require the F02 `Authorization: Bearer` access token. The
recipient account comes only from the authenticated principal. Notification
IDs are not authorization credentials; reads and updates are always filtered
by the recipient. A cross-account or missing notification uses the same
privacy-safe `404 NOT_FOUND`.

## Routes

| Method and path | Behavior |
| --- | --- |
| `GET /api/v1/notifications?status=all&limit=20&cursor=...` | List notifications; `status` is `all`, `unread`, or `read` |
| `GET /api/v1/notifications/{notificationId}` | Read one notification owned by the caller |
| `GET /api/v1/notifications/unread-count` | Return the caller's unread count |
| `PATCH /api/v1/notifications/{notificationId}/read` | Mark one notification read; idempotent |
| `PATCH /api/v1/notifications/read` | Mark all caller-owned unread notifications read |

Page size is 1–50, defaults to 20, and uses a keyset cursor ordered by
`createdAt` descending and ID descending. Cursors are bound to the selected
status and invalid cursors return `422 INVALID_CURSOR`. New notifications
created ahead of a cursor do not move the cursor boundary. Concurrent read
state changes can naturally move an item between `unread`, `read`, and `all`
views. The response shape is `{ "items": [], "nextCursor": null }`.

## DTO

```json
{
  "id": "c1b2a3d4-e5f6-4789-8012-3456789abcde",
  "kind": "friend_request",
  "actor": {
    "accountId": "b1c2d3e4-f5a6-4789-8012-3456789abcde",
    "displayName": "Alex Example",
    "username": "alex_example"
  },
  "destination": {
    "type": "profile",
    "id": "b1c2d3e4-f5a6-4789-8012-3456789abcde"
  },
  "createdAt": "2026-11-27T14:00:00Z",
  "readAt": null
}
```

`kind` is a validated lowercase identifier, not a closed enum; consumers must
gracefully handle unknown future kinds. Initial planned kinds include
`friend_request`, `friend_accepted`, `room_invitation`,
`playlist_invitation`, `playlist_updated`, and `room_activity`. Producers for
friendship and room events are implemented with those resource features.
Playlist invitation and invitation-state producers are implemented with F07.

Actor summaries include only the account ID, display name and username that
the current profile contract makes visible to profile viewers. They exclude
bio, location, genres, email, and arbitrary producer text. If the actor account
or profile is gone, `actor` is `null`.

Destinations contain only a typed opaque reference, never a resource title,
message, invitation payload, or permission. Supported types are `profile`,
`playlist`, and `room`. A deleted profile destination is returned as `null`.
Playlist resources now exist; F07 creates invitation notifications only after
the owner-authorized operation commits its domain changes. Room resource
models/producers are not implemented. Every resource endpoint/navigation
action must recheck current authorization; possessing a notification or
reference grants no access. Missing or inaccessible resources must retain
their resource feature's privacy-safe behavior. Destination visibility is not
rechecked by the notification read API.

Unread count:

```json
{ "unreadCount": 2 }
```

Mark-all response:

```json
{ "updatedCount": 2 }
```

`createdAt` and `readAt` are generated by PostgreSQL in UTC and serialized as
RFC 3339 timestamps. Marking an already-read item returns its original
`readAt`; marking all affects only unread rows and returns the number changed.
An account deletion cascades its recipient notifications; deletion of an actor
clears the actor reference.

## Producer contract

There is deliberately no public notification-create endpoint. Domain producers
call `app.notifications.service.create_notification` inside their transaction
and supply the authenticated/authorized recipient, a stable producer event
UUID, a supported kind, an optional actor account, and an optional typed
destination. They must not accept client-authored notification text or treat
an arbitrary client destination ID as authorized.

Idempotency is scoped to `(recipientAccountId, producerEventId)`. Re-delivery
with the same key and identical actor/kind/destination returns the original
notification and does not change timestamps or read state. Reusing the key
with different notification data raises `NotificationIdempotencyConflict`;
producers should log only the event ID/correlation metadata, not payloads.
Different recipients may receive notifications for the same source event.

Profile/friendship, playlist, and room features still own their specific
producer calls and resource access rules. In particular, this contract does
not implement invitation acceptance/rejection behavior or authorize navigation
to a playlist or room. Notification API logs do not include bearer tokens or
notification payloads.
